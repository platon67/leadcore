# 04 — Architecture n8n

Partie de l'[Operating System outbound & delivery](README.md).

Trente workflows partagés par les deux moteurs et tous les clients. Aucun
workflow n'est copié par client : le client est un paramètre (`client_id`),
sa configuration vit dans `client_config`.

---

## D0 — Conventions

| Règle | Détail |
|---|---|
| Nommage | `LC-0xx — Nom court` ; sous-workflows `LC-0xx.a` |
| Moteur | Tag `moteur:A`, `moteur:B` ou `moteur:AB` sur chaque workflow |
| Idempotence | Chaque exécution porte une clé (`source:source_id`, `message_id`, `event_id`). Un webhook reçu deux fois ne crée rien deux fois : contrainte d'unicité en base, `INSERT … ON CONFLICT DO NOTHING` |
| Écriture | Toute écriture passe par Postgres d'abord, puis vers les outils (séquenceur, Attio). Jamais l'inverse sans resynchronisation |
| Journal | Chaque changement d'état écrit un `event` (05-DONNEES) |
| Erreurs | Chaque workflow a un Error Trigger vers **LC-028** ; 3 tentatives avec attente exponentielle sur les appels HTTP ; au-delà, file `dead_letter` |
| Secrets | Credentials n8n chiffrés ; aucune clé dans le code des nœuds ; clé de chiffrement n8n sauvegardée hors du serveur |
| Environnements | `staging` (données factices, séquenceur en mode test) et `production` ; export JSON des workflows versionné dans un dépôt privé |
| Débits | Nœud d'attente entre appels selon la limite de chaque API (Sirene, Apollo, France Travail 10/s, Smartlead) |
| Mode d'exécution | Mode `queue` (Redis + workers) dès le palier STANDARD |
| IA | Appels Claude via le nœud HTTP ou le nœud Anthropic, sortie en JSON validée par schéma ; échec de validation = nouvel essai puis revue humaine |

Format de chaque fiche : **TRIGGER → STEPS → CONDITION → ACTION → DATABASE →
NOTIFICATION**.

## D1 — Acquisition de données

### LC-001 — Prospect ingestion

```
TRIGGER   Cron lundi 6 h (moteur A) · Webhook « nouvelle campagne » (moteur B, depuis LC-015) · Upload CSV
   ↓
STEP 1    Lire la requête (segment_query) : source, filtres, volume visé
STEP 2    Appeler la source (Sirene / Apollo / import CSV), paginer, respecter le débit
STEP 3    Écrire chaque ligne brute dans raw_record (source, source_id, payload JSON, fetched_at)
STEP 4    Normaliser (sous-workflow LC-001.a) : domaine, raison sociale, nom, titre → fonction
   ↓
CONDITION Domaine ou SIREN présent ?  non → raw_record.status = 'incomplete'
          Déjà en suppression (domaine, email, SIREN) ?  oui → 'suppressed'
   ↓
ACTION    Upsert company (clé SIREN > domaine) ; upsert contact (clé email > nom+domaine)
DATABASE  raw_record, company, contact, event(type='ingested')
NOTIFICATION Slack #data : « 1 240 lignes, 1 102 nouvelles, 38 supprimées, 100 incomplètes »
          Alerte si volume < 50 % du volume visé
```

### LC-002 — Lead enrichment & verification

```
TRIGGER   Fin de LC-001 · Cron toutes les heures (contacts 'to_enrich')
   ↓
STEP 1    Sélectionner les contacts dont le compte a passé les filtres éliminatoires
          (on n'enrichit jamais un compte hors ICP : c'est le premier coût caché, 03-STACK C4)
STEP 2    Waterfall email : Apollo (si pas d'email) → FullEnrich → Dropcontact (Europe)
STEP 3    Pappers pour les comptes FR sans données financières
STEP 4    Crawl du site (5 pages) si absent ou > 90 jours ; résumé Haiku (offre, cibles, preuves)
STEP 5    Vérification MillionVerifier
   ↓
CONDITION status = valid → 'ready' · catch_all + trouvé par fournisseur → 'ready_catchall'
          catch_all deviné → 'ready_catchall_guessed' (comptes A seulement)
          invalid / unknown → 'invalid'
   ↓
ACTION    Écrire email, statut, provider, coût unitaire
DATABASE  contact, company, enrichment_log (provider, coût, résultat), event
NOTIFICATION Hebdo : taux de trouvaille et coût par fournisseur ; alerte si taux de trouvaille d'un fournisseur chute de > 30 %
```

### LC-015 — Client lead sourcing (moteur B)

```
TRIGGER   Brief ICP validé (B2) · Segment restant < 2 mois de production (LC-022)
   ↓
STEP 1    Lire icp_card (JSON) du client
STEP 2    Générer les requêtes (table B3.1) : Sirene, Apollo, France Travail
STEP 3    Estimer la taille : compte des comptes Sirene par segment
STEP 4    Écrire la carte du marché (segments, volumes, mois de production)
   ↓
CONDITION Volume total < 12 mois de production ?  → alerte « refus de mission possible » (règle du document de référence)
   ↓
ACTION    Créer les segment_query ; déclencher LC-001 pour le segment 1
DATABASE  icp_card, segment, segment_query, market_map
NOTIFICATION Campaign manager : carte du marché prête (livrable J5) ; client : lien vers la carte
```

### LC-016 — Signal ingestion

```
TRIGGER   Cron quotidien 5 h
   ↓
STEP 1    France Travail : offres des dernières 24 h sur les codes ROME et mots-clés suivis
STEP 2    BODACC / Pappers : modifications (dirigeants, établissements, procédures) sur les SIREN suivis
STEP 3    TheirStack (si actif), import Sales Nav (CSV du lundi), liste des levées, crawl diff
STEP 4    Rapprochement : SIRET → SIREN → domaine → nom + CP (similarité)
   ↓
CONDITION Similarité ≥ 0,9 → signal créé · 0,7-0,9 → file de validation humaine · < 0,7 → ignoré
          Procédure collective → suppression du compte (K7)
   ↓
ACTION    Créer signal (type, fait, date, source, url, poids) ; déclencher LC-003 pour le compte
DATABASE  signal, event
NOTIFICATION Résumé quotidien ; file de validation dans Slack (boutons oui/non)
```

## D2 — Scoring et campagnes

### LC-003 — ICP scoring

```
TRIGGER   Fin de LC-002 · Nouveau signal (LC-016) · Cron trimestriel (recalcul complet)
   ↓
STEP 1    Charger le modèle de score actif (score_model : version, poids) du moteur ou du client
STEP 2    Appliquer les filtres éliminatoires ; calculer les points ; signal_score avec décroissance
STEP 3    Déterminer le palier (A/B/C/D)
   ↓
CONDITION Palier monté à A à cause d'un signal ?  → file prioritaire du jour
   ↓
ACTION    Écrire score, palier, score_version, détail des points (JSON)
DATABASE  company_score (historisé), event(type='scored')
NOTIFICATION Aucune (sauf passage en A : ligne dans le résumé du setter)
```

### LC-004 — Campaign assignment

```
TRIGGER   Cron lundi 8 h · File prioritaire (passage en A)
   ↓
STEP 1    Pour chaque segment actif, prendre les contacts 'ready' non contactés, ordonnés par score
STEP 2    Appliquer la matrice A5 (strategy_rule) : persona, signal → douleur → angle → offre → CTA
STEP 3    Répartir entre témoin (80 %) et exploration (20 %) selon experiment
STEP 4    Contrôle de capacité (LC-021) : taille du lot autorisée cette semaine
   ↓
CONDITION Contact dans une autre campagne active, ou contacté par Leadcore < 60 jours (B4.2) ?  → exclu
   ↓
ACTION    Créer lead (contact × campagne × variante), lot daté
DATABASE  lead, batch, event(type='assigned')
NOTIFICATION Récap : lots de la semaine par campagne
```

### LC-005 — AI personalization

```
TRIGGER   Cron 20 h (lot du lendemain)
   ↓
STEP 1    Sélectionner les leads du lot selon leur niveau (N2/N3/N4)
STEP 2    N2/N3 : construire les requêtes Message Batches (Haiku 4.5, prompt 12-PROMPTS P2), prompt système en cache
STEP 3    N4 : Sonnet 5 avec recherche web (P3), un par un, file de relecture humaine
STEP 4    Récupérer les résultats (poll jusqu'à 'ended'), clé par custom_id = lead_id
   ↓
CONDITION JSON valide et champ 'sources' non vide ?  non → nouvel essai, puis N1 (pas de ligne perso)
   ↓
ACTION    Écrire ligne_perso, sources utilisées, modèle, coût
DATABASE  lead.personalization, ai_call_log
NOTIFICATION File N4 à relire (setter) ; coût IA du jour
```

### LC-006 — Email QA

```
TRIGGER   Cron 7 h · Fin de LC-005
   ↓
STEP 1    Rendre chaque email (template + variables)
STEP 2    Portes automatiques Q1-Q7, Q9 (A9.3)
STEP 3    Juge Haiku (P4) sur la ligne personnalisée : fait sourcé, ton, longueur
STEP 4    Tirer 10 emails au hasard → message Slack avec boutons « OK / bloquer le lot »
   ↓
CONDITION Porte bloquante rouge ?  → lot en 'blocked' · Relecture humaine non faite à 10 h ?  → lot reporté (jamais envoyé sans relecture)
   ↓
ACTION    Lot 'approved'
DATABASE  batch.qa_result, event
NOTIFICATION Opérateur : résultat QA ; alerte si blocage
```

### LC-007 — Campaign sending

```
TRIGGER   Lot 'approved'
   ↓
STEP 1    Créer ou mettre à jour la campagne dans le séquenceur (API) : séquence, boîtes, horaires
STEP 2    Pousser les leads avec leurs variables (API, par paquets)
STEP 3    Vérifier le nombre de leads acceptés vs poussés
   ↓
CONDITION Écart > 0 ?  → réconciliation, alerte
          Boîte assignée en état non vert (LC-017) ?  → retirée de la campagne
   ↓
ACTION    Lead 'sequenced' avec l'id du séquenceur
DATABASE  lead, campaign.external_id, event(type='sequenced')
NOTIFICATION Aucune (sauf écart)
```

Les envois eux-mêmes sont faits par le séquenceur. n8n reçoit ses webhooks
(`email_sent`, `email_bounced`, `reply_received`, `lead_unsubscribed`) et les
écrit en `message` et `event`.

## D3 — Réponses et rendez-vous

### LC-008 — Reply classification

```
TRIGGER   Webhook séquenceur 'reply_received'
   ↓
STEP 1    Dédoublonner (message_id) ; retrouver lead, contact, campagne, client
STEP 2    Nettoyer : retirer la citation du message précédent, la signature
STEP 3    Détecteur rapide d'opposition (mots-clés : stop, désinscri, retirez, ne plus, unsubscribe, RGPD, CNIL…)
STEP 4    Classification Haiku 4.5 (P5) : classe, confiance, date de rappel, personne référée, objection, concurrent cité
   ↓
CONDITION Mots-clés d'opposition OU classe UNSUBSCRIBE/HOSTILE → LC-023 immédiatement, quelle que soit la confiance
          Confiance < 0,8 → classe proposée + revue humaine
   ↓
ACTION    Arrêter la séquence du lead dans le séquenceur ; router selon la classe (A11.1)
DATABASE  reply (texte, classe, confiance, attributs), lead.status, event
NOTIFICATION POSITIVE / QUESTION / OBJECTION / REFERRAL → fiche dans la file du setter (Slack + Attio / vue client)
```

### LC-009 — Positive reply routing

```
TRIGGER   reply.class ∈ {POSITIVE, QUESTION, OBJECTION, REFERRAL}
   ↓
STEP 1    Construire la fiche : compte, score, signaux, fil complet, résumé du site
STEP 2    Brouillon de réponse (Sonnet 5, P6) : 2 créneaux lus dans l'agenda cible (Cal), FAQ, objections
STEP 3    Priorité de booking (A13) ; assignation au setter (charge, niche)
   ↓
CONDITION Moteur A → opportunité Attio · Moteur B → opportunité dans la vue client
          Pas de validation du setter en 1 h ouvrée → relance, puis escalade au responsable à 2 h
   ↓
ACTION    Envoi par le setter depuis la boîte d'origine (même fil) après validation
DATABASE  opportunity, task, reply.draft, event
NOTIFICATION Slack du setter (mention), compteur de SLA
```

### LC-010 — Booking

```
TRIGGER   Webhook Cal 'BOOKING_CREATED' · Setter qui crée le RDV à la main
   ↓
STEP 1    Rattacher le RDV à l'opportunité (email du participant)
STEP 2    Vérifier les critères du RDV qualifié du client (questions du formulaire Cal + fiche)
STEP 3    Moteur B : pousser le RDV dans le CRM du client s'il est connecté ; envoyer la fiche RDV au commercial
   ↓
CONDITION Critère manquant → RDV marqué 'non_qualifié', validation client requise avant d'être compté
   ↓
ACTION    Créer meeting (statut 'booked') ; programmer LC-018
DATABASE  meeting, opportunity.stage, event
NOTIFICATION Commercial concerné (Leadcore ou client) ; setter
```

### LC-018 — Meeting reminders & no-show

```
TRIGGER   Création de meeting · Cron toutes les 15 min
   ↓
STEP 1    Confirmation immédiate (email) ; J-1 (email avec question « toujours bon ? ») ; H-2 (SMS)
STEP 2    À H+1 après le début : demander le statut (moteur A : closer ; moteur B : formulaire client J+1)
   ↓
CONDITION no_show_prospect → séquence de replanification (2 messages / 48 h), une seule fois
          client_cancel → statut facturable à 50 % (politique no-show)
          réponse « annuler » au J-1 → proposer 2 nouveaux créneaux
   ↓
ACTION    Mettre à jour meeting.status : held / no_show / rescheduled / client_cancel / cancelled
DATABASE  meeting, reminder_log, event
NOTIFICATION Setter en cas de no-show ; alerte si statut non renseigné à J+2
```

### LC-025 — J+30 follow-up

```
TRIGGER   Cron quotidien : meetings 'held' atteignant J+30
   ↓
STEP 1    Envoyer au client un formulaire par RDV (perdu / en cours / signé + montant, motif si perdu)
STEP 2    Relance à J+33 ; au-delà, ajout à l'ordre du jour du point mensuel
   ↓
CONDITION Statut 'signé' → mettre à jour le lookalike (B7) et le score client

ACTION    Écrire meeting_outcome
DATABASE  meeting_outcome, event

```

## D7 — Conformité, nurture, facturation, exploitation

### LC-023 — Suppression & opposition

```
TRIGGER   LC-008 (UNSUBSCRIBE, HOSTILE, mots-clés) · webhook séquenceur 'unsubscribed' · lien d'opposition (page) · demande par email / courrier (saisie manuelle)
   ↓
STEP 1    Ajouter à suppression : email ; et selon la demande, domaine entier
STEP 2    Arrêter toutes les séquences du contact, **dans tous les clients et les deux moteurs**
STEP 3    Pousser vers la blocklist globale des séquenceurs (Smartlead et Instantly)
STEP 4    Si demande d'effacement (art. 17) : purge des données personnelles, conservation d'une empreinte (hash) de l'email en suppression pour ne pas recontacter
   ↓
CONDITION Contact en RDV à venir ?  → alerte humaine (cas rare, à traiter à la main)
   ↓
ACTION    Confirmation au demandeur si la demande l'appelle
DATABASE  suppression, contact (purge éventuelle), event(type='opt_out')
NOTIFICATION Journal de conformité ; délai de traitement mesuré (objectif < 1 h, maximum légal 1 mois)
```

désinscriptions.
